What v1 looks like

Every screen in the v0.1 milestone — the first release a citizen could use — drawn at size. Fifteen on a phone, two on the web.

Each one is marked with what exists today, so the gap between the design and the code is visible rather than assumed.

These are sketches for orientation. docs/02-product/11-screen-spec.md is the authority: where it and a picture here disagree, the file wins. Sample data is illustrative — no real contractor is named, and the one place a name would appear shows the below-threshold copy instead.

Working today

  • Backend, deployed and live over HTTPS with a valid certificate
  • Accounts — email and password; duplicate, weak and malformed addresses refused
  • Sessions — signed tokens; a tampered, rewritten or alg:none token is refused
  • Capture — photograph plus position, stored before the reply, attributed to whoever sent it
  • Retry-safe — the same capture twice gives one report and one photograph
  • Collection — BMC works data archived twice a day, 4,673 records

Not there yet

  • The pipeline — classification, jurisdiction, contract attribution. Thirteen of these screens wait on it
  • Rate limiting — twelve wrong passwords in a row were all answered at full speed
  • Password reset — a forgotten password means a new account
  • Email verification — any address can be registered, owned or not
  • Token revocation — signing out clears the device, not the token
  • Phone verification — the gate before anything becomes public
  • Built and working today
  • Partly built
  • Not built yet

On a phone

The capture path is the product. Everything from S01 to S07 exists to get one honest photograph, geotagged, into the system without asking the citizen to type anything.

On the web

Two pages, both public, both server-rendered with no login and a 2G budget. This is where a shared link lands — and where anyone can check the platform's own numbers.

What stands between here and v1

Capture works end to end today, against a deployed backend rather than a laptop: a photograph and a position reach the server, are stored before the reply, survive a retry, and are attributed to the account that sent them. That last part was a bug — every report was being filed under one shared account — found by checking the database rather than trusting the code, and fixed on 25 September.

Everything else on these screens depends on three pieces that do not exist yet, in this order:

  • Classification — what is in the photograph. Unlocks S04, S06, S16.
  • Jurisdiction — which ward and department own that point, and the confidence gate that decides when to ask the one question. Unlocks S04, S05, S06, S15.
  • Attribution — joining the point to a contract in the works data already collected twice a day. Unlocks S08, S09, S14 — and it is the thesis of the whole product.

After those: the share kit (S10), issue state and its timeline (S11, S12), the public web pages (S14, S15), and phone verification (S13), which gates anything public.

Auth itself holds up where it was tested — a duplicate address, a weak password, a tampered token, a payload rewritten to another account and an alg:none forgery are all refused, and a wrong password is answered identically to an address that was never registered, so the service cannot be used to discover who has an account. What is missing is everything around it: rate limiting (twelve wrong passwords in a row were answered at full speed), password reset, email verification and token revocation. None is a bug; each is a reason this is not ready for anyone but its operator.

Four rules shaped every screen above, and are worth stating plainly because they are what makes this different from the platforms that came before it: nothing is ever filed by the platform — every instrument is a draft a person reviews and submits; no fact about a named party appears without a source and a retrieval date; nothing asserts wrongdoing, only what happened and when; and “authority says fixed” is never the same thing as “a citizen photographed it fixed”.
